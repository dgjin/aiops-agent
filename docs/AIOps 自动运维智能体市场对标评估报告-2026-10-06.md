## 一、市场坐标系：2026 年的 AI 自动运维玩家

当前市场（2026）已从「告警聚合 + 脚本化 Runbook」进化到「LLM Agent 闭环处置」阶段，主流产品按能力前缀可归为四类：

| 类别 | 代表产品 | 核心特征 |
|---|---|---|
| **调查型 Agent** | Resolve AI（估值 $1B）、Traversal、Vibe OnCall | 以「假设生成树 + 定向遥测探测」替代人肉排查，输出根因结论与证据链；**不做自动变更** |
| **平台内嵌 SRE Agent** | Datadog Bits AI SRE、Azure SRE Agent（2026-03 GA）、PagerDuty SRE Agent | 绑定自有可观测/云平台数据，调查能力强、生态闭环强；变更执行受平台边界限制 |
| **自动化执行与护栏** | Anyshift、OpsWorker、Cleric | 以「安全护栏 + 变更执行」为主卖点，强调审批、审计、回滚；调查宽度依赖外部数据源 |
| **指挥协同控制台** | incident.io 等 | 面向事件指挥（Incident Command），协调人、任务、状态同步；自动化执行较弱 |

行业共识工作流（四阶段）：**环境图谱构建 → 假设生成树 → 定向遥测探测 → 信任梯度处置**。

行业铁律：**"Don't turn on autonomous remediation on day one"** —— 所有头部产品都以「先建议、后审批、再自动」的 graduated trust（渐进信任）路径上线，无人直接开启全自动修复。

参照系定位结论：本项目属于「**自动化执行与护栏**」类别的自建形态——调查层相对薄（依赖单一日志源 + LLM triage），但**处置闭环深度（修复→沙箱→审批→金丝雀→回滚）在自建项目中属于第一梯队**。

## 三、优势解读（六条）

1. **真闭环，不是 Demo 玩具**：Alerts → Loki 取证 → Drain3 聚类 → LLM triage → Code RAG → LLM 补丁 → Docker 沙箱真执行 → 人工审批 → 公告倒计时 → 金丝雀真发布/真回滚，全链每一环都有真实执行器与实测证据（wp9-final-1 全链路 DONE，71.6s）。
2. **三道闸门 + fail-closed 姿态**：低置信度（<0.8）转人工、受保护目录（auth/payment/crypto）二级审批、公告 15 分钟倒计时；kill switch 状态不可读时直接拒绝新流程。这与行业「graduated trust」铁律同频——**默认不信任，不确定即转人工**。
3. **量化评测基线先行**：triage_eval（6 样本 100% 准确 / 均 1.18s）与 fix_eval（qwen3:8b 沙箱 0/2 vs qwen3.8:27b-mlx 2/2）给出可复现的数字，并得出「模型档位直接决定修复成功率」的业务结论。自建项目中有量化闭环的极少。
4. **双模架构与企业级生产化**：单一代码库 demo（零依赖文件后端）/ production（MySQL 8 + RBAC + 令牌仅存 sha256 + K8s 清单 + TTL 清理）双档运行，互不影响。多数同类自建项目止步于单机脚本。
5. **工程密度高**：6 个常驻组件（worker/BFF/webhook/prober/ship/surge）全本地可跑，一键编排 9 步 + 8 个演示剧本 + doctor 自检 7 项 + 全量测试 531 passed，交付成熟度远超原型。
6. **无云依赖**：LLM 走本机 Ollama（qwen3 系列），数据不出内网，对数据敏感型场景（金融/政企）是结构性优势，也是成本优势。

## 四、短板解剖

### P0（天级，影响可信度与安全底线）
1. **webhook 接入无鉴权**：`alert_webhook.py` 对 `/webhook` 不校验任何凭证（无 authorization/secret/token 字段，已代码核验）。任何能访问 8099 端口的人可伪造告警 → 触发 AI 改代码 + 走发布链路的完整流程。在「自动改生产代码」的系统里，这是最严重的攻击面。
2. **CI 全形态缺失**：`.github/`、`.gitlab-ci.yml`、gitee 流水线均不存在（已核验）。531 个测试、Bandit 扫描、前端构建全靠本地自觉执行，无任何合入门禁。「-t . 测试命令」这类血泪教训无法被机制固化。
3. **组件守护缺失**：`demo-up.sh` 只负责启动，不负责守护。6 个常驻组件任一崩溃（worker/BFF/webhook/prober/ship/surge），链路即静默断裂——没有告警、没有自动拉起，直到下次用户发现问题。

### P1（周级，影响运营质量）
4. **变更关联缺失**：发布事件未进入 triage 上下文。「刚发版就崩」这类最高频根因场景，LLM 拿不到最近变更信息。
5. **无 shadow mode**：缺少「只建议不执行」模式。行业铁律是先跑 shadow 积累信任，本系统目前只有「全自动 + 闸门」单档。
6. **ESCALATED 无处置闭环**：升级人工后仅剩 KPI 计数，没有待办列表、责任人指派、超时再升级等处置通道。
7. **运营度量面板缺失**：有指标数据（Prometheus/审计），但没有「MTTR / 自动修复率 / 人工干预率 / 闸门拦截率」的运营视图。
8. **评测样本量偏小**：triage 6 样本 / fix 2 样本，统计置信度不足，需扩到 30+ 样本才有说服力。

### P2（月级，影响天花板）
9. **事件聚合层缺失**：多告警并发时逐条开流程，无「同故障域聚合为一个事件」的能力（对照：行业事件聚合降噪是标配）。
10. **无服务拓扑**：triage 没有依赖拓扑上下文，无法回答「根因在上游还是下游」。
11. **无 ChatOps 入口**：查询/审批只能在控制台操作，IM 里只能收到通知不能操作。
12. **无对外能力暴露**：没有 MCP server / OpenAPI 形态，无法被外部 Agent 平台（如企业内其他智能体）编排调用。

### P3（战略级，影响定位）
13. **定位收敛**：功能面（感知/调查/修复/发布/审批）全都要 vs 市场产品的单点极致，需明确主战场（建议：中小团队「无人值守夜间修复」场景）。
14. **商业化假设**（若走）：多租户、SSO、审计导出、等保合规是前置门槛，当前单租户架构需重构。

## 六、总评评分（10 分制）

| 维度 | 得分 | 说明 |
|---|---|---|
| 闭环深度 | **9** | 修复→沙箱→审批→金丝雀→回滚全链真实执行，自建项目第一梯队 |
| 调查宽度 | **5** | 单一日志源 + LLM triage，缺拓扑、变更关联、事件聚合（P1-1 变更关联、P2-1 事件聚合、P2-2 浅拓扑落地后升至 7） |
| 安全基线 | **6** | 控制台侧完备（RBAC/令牌/kill switch），接入侧曾有零鉴权缺口（P0-1 修复后升至 8） |
| 生态集成 | **4** | IM 通知 + 三平台 MR + 可观测数据源，无对外接口形态（P2-3 ChatOps、P2-4 MCP 落地后升至 6） |
| 工程密度 | **9** | 7 组件（含 MCP 出口）+ 双模 + 991 测试 + K8s 清单 + 8 剧本，成熟度远超原型 |
| 生产验证 | **4** | 全链路实测充分，但均为自造场景（无真实线上流量/外部用户验证） |

**结论**：本项目在「自动修复闭环 + 安全闸门」两个维度上具备与 2026 主流商业产品对标的能力，核心差距在**调查宽度**（拓扑/变更/聚合）与**生态与生产验证**。P0 三条（鉴权/CI/守护）是可信度底座、P1 五条（变更关联/shadow/处置闭环/度量面板/评测扩样）是运营质量补强，均已全部落地（见附录）；P2 四条（事件聚合/浅拓扑/ChatOps/MCP）亦已全部落地（见附录）；P3 定位收敛建议按需启动。
