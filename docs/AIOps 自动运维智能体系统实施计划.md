## 1. 实施总策略

1. **分期递进、闸门先行**：一期只做「可见可诊断」（监控 + 分析 + 修复建议），二期引入人工闸门（沙箱测试 + 审批），三期才全自动发布。每期设**出口门禁**，指标达标才进入下一期，未达标加固迭代。
2. **骨架先行、桩逐替换**：以已评审的 Temporal 工程骨架（`workflow / activities / config / models`）为蓝本，先用演示桩跑通三道闸门端到端流程，再逐个将 activity 桩替换为真实实现，避免流程与实现脱节。
3. **策略即配置**：所有闸门行为从第一天起就走 `release-gate-policy.yaml` + pydantic 强校验 + 启动快照，不硬编码；运行期不热修改，变更走版本升级与评审。
4. **默认安全侧**：所有不确定路径（超时、弃权、接口异常）一律走驳回或转人工；全程保留手动发布通道与全局 kill switch。
5. **指标驱动验收**：每期定义量化验收指标（Top-1 命中率、采纳率、审批时长、MTTR、回滚成功率），用数据说话。

## 3. 一期实施计划（W1–W8）：感知 + 分析 + 修复建议

### WP1 监控与告警接入（W1–W2）

- **目标**：打通异常发现链路，产出标准告警事件 `Alert{alert_id, service, severity, description}` 作为流程唯一入口。
- **任务**：
  1. Prometheus 抓取应用与主机指标（QPS、错误率、延迟、资源水位）；
  2. Alertmanager 规则配置（阈值 + 同比/环比基线），配置分组与抑制防告警风暴；
  3. 告警标准化适配器：Alertmanager webhook → `Alert` 模型；
  4. Temporal 工作流幂等启动（`WORKFLOW_ID_REJECT_DUPLICATE`），重复告警不重复开流程。
- **交付物**：告警接入服务、告警规则集 v1、告警 → workflow 联通验证报告。
- **验收**：模拟阈值越限，30 秒内生成 Alert 并启动 workflow；重复投递同一告警不产生第二个流程实例。
- **依赖**：Prometheus / Alertmanager 环境（已有或需补齐）。

### WP2 日志采集与聚类降噪（W2–W3）

- **目标**：日志按服务与 trace_id 关联入库，重复日志聚类聚合，避免淹没 LLM 上下文。
- **任务**：
  1. Filebeat / Fluent Bit → Loki（或 ELK）采集管道，统一 trace_id 关联字段规范；
  2. Drain3 模板聚类服务：同模板海量重复日志聚合为计数（聚类在采集侧完成）；
  3. 错误日志突增检测（同比/环比基线），超限触发告警事件。
- **交付物**：日志管道、Drain3 聚类服务、突增检测规则。
- **验收**：重复日志聚类压缩后单事件日志量可控；错误日志突增 1 分钟内触发告警。
- **依赖**：WP1（告警入口）。

### WP3 LLM 根因分析（W3–W5）

- **目标**：输出结构化根因，落地闸门 1（策略闸门）。
- **任务**：
  1. OpenTelemetry 调用链接入，为根因分析提供跨服务上下文；
  2. Triage prompt 工程与结构化输出 schema：`error_type` / `suspect_files` / `confidence` / `summary`（pydantic 校验）；
  3. 置信度评分机制；**闸门 1 规则：confidence < 0.8 直接转人工**，流程结束并留痕；
  4. 历史工单库接入（为 WP4 RAG 准备语料）。
- **交付物**：triage 服务、根因 schema、闸门 1 拦截逻辑。
- **验收**：根因输出 100% 通过 schema 校验；离线回放历史故障，低置信度样本 100% 转人工；测量 Top-1 命中率基线。
- **依赖**：WP2、LLM API 接入与额度。

### WP4 Code RAG 与修复建议（W5–W7）

- **目标**：检索相似历史修复，生成最小化补丁 diff 与变更说明（一期只输出建议，人工执行发布）。
- **任务**：
  1. 代码仓库 AST 语义切块 + 向量索引建库（向量库选型与部署）；
  2. 检索相似缺陷的历史修复方案作为生成上下文；
  3. 修复 Agent：生成**最小化 diff** + 变更说明 + 风险评估；优先单点修复，禁止顺手重构；
  4. 变更白名单与受保护目录判定逻辑（`auth/**`、`payment/**`、`crypto/**`）先行落地（供二期闸门直接调用）；
  5. 补丁元数据标签 `ai-fix: {alert_id, model_version, confidence}`。
- **交付物**：代码索引 pipeline、修复 Agent、建议输出通道（IM 卡片 / MR comment）。
- **验收**：建议 diff 可编译（骨架演示验证）；标签字段完整；人工可按建议执行发布并反馈采纳结果。
- **依赖**：WP3、代码仓库只读权限、向量库。

### WP5 工程骨架与策略配置（W1–W7 贯穿）

- **目标**：Temporal 工程骨架全量落地，策略配置化、可评审、可回滚。
- **任务**：
  1. 落地 `aiops-agent/` 骨架：`config.py` / `models.py` / `activities.py` / `workflows.py` / `worker.py` / `demo_cli.py`；
  2. `release-gate-policy.yaml` 全量键位 + pydantic 强校验，**启动快照**加载、运行期不热修改；
  3. 审计字段（设计方案附录 B）在每阶段收尾时写入；
  4. 同一服务 24h 内 AI 自动修复次数上限（防修复风暴）。
- **交付物**：可运行工程骨架、策略配置 v1、审计记录结构。
- **验收**：`demo_cli.py` 跑通三道闸门桩流程；非法配置在启动阶段即报错退出；审计记录可查询。
- **依赖**：Temporal 服务端。

### WP6 一期联调与验收（W7–W8）

- **任务**：仿真告警全流程演练；指标看板（Top-1 命中率、建议采纳率）；一期评审会。
- **出口**：指标达标 → 进入二期；未达标 → 针对性加固后再评审。

## 4. 二期实施计划（W9–W16）：沙箱测试 + 自动 MR + 审批闸门

### WP7 测试沙箱（W9–W11）

- **目标**：补丁在强隔离环境中执行验证。
- **任务**：
  1. 独立 K8s Job + gVisor / Firecracker 强隔离运行时；
  2. **补丁无出网权限**（NetworkPolicy 强制），依赖安装走内网镜像/缓存加速；
  3. 沙箱并发配额，防资源争抢。
- **交付物**：沙箱运行时、隔离策略、配额配置。
- **验收**：沙箱内样例单测执行成功；出网请求验证被阻断；隔离逃逸测试（红队）通过。
- **依赖**：K8s 集群、gVisor/Firecracker 运行时。

### WP8 测试流水线与质量门禁（W11–W13）

- **任务**：
  1. 单元测试 + 回归测试编排；
  2. SAST 静态扫描（禁止引入高危漏洞 / 敏感信息硬编码）；
  3. 质量门禁：任一环节失败回炉重试（**限次**，次数入配置，防 token / 资源雪崩）；仍失败 → ESCALATED 转人工。
- **交付物**：测试流水线、门禁策略、ESCALATED 分支逻辑。
- **验收**：故意注入失败用例 → 正确拦截；限次重试耗尽后转人工并留痕。
- **依赖**：WP7。

### WP9 自动创建 MR（W13–W14）

- **任务**：GitLab CI / GitHub Actions 集成；自动创建 MR + 补丁标签；MR 描述含根因、测试报告、回滚预案。
- **验收**：从告警到 MR 生成全流程无人工干预；产物可追溯至 alert_id。
- **依赖**：WP8、代码仓库写权限。

### WP10 审批闸门（闸门 2）（W13–W16）

- **任务**：
  1. IM 交互卡片（飞书 / 钉钉 / Slack），含**根因分析、完整 diff、测试报告、回滚预案**四部分；
  2. Signal 接口：`submit_approval`（approve / reject）、`submit_second_approval`；
  3. **超时策略（锁定）**：等待 30 分钟无响应 → 自动驳回，同时电话/短信升级值班负责人；驳回即关闭流程并留痕；
  4. 受保护目录（`auth/**`、`payment/**`、`crypto/**`）补丁追加**二级审批**卡片；
  5. 人工在环原则：超时、弃权、接口异常一律走向驳回 / 转人工，绝不自动放行。
- **交付物**：审批卡片服务、双级审批流、超时升级通道。
- **验收**：超时演练正确触发自动驳回 + 电话升级；二级审批演练通过；卡片一键操作闭环。
- **依赖**：WP9、IM 机器人应用权限、电话/短信通道。

### 二期联调与验收（W16）

- 测试通过率、审批平均时长统计看板；全链路演练（告警 → 沙箱 → MR → 审批 → 人工发布）。
- 出口：指标可统计且达标 → 进入三期。

## 5. 三期实施计划（W17–W24）：公告 + 延迟发布 + 金丝雀回滚

### WP11 用户通知与公告（W17–W19）

- **任务**：
  1. WebSocket 向所有在线会话推送站内弹窗 + 页面 Banner，可选 App Push；
  2. 公告模板（含影响范围与时间）；公告内容与发布时间入审计日志；
  3. 倒计时**以服务端时间为准**，客户端只做展示。
- **验收**：多端弹窗一致性验证；公告记录可审计追溯。
- **依赖**：二期验收通过。

### WP12 15 分钟延迟发布队列（W17–W20）

- **任务**：
  1. 部署任务写入持久化延迟队列（Temporal 定时器），服务重启、worker 宕机任务不丢；
  2. window 内四类事件处理（**锁定策略**）：
     - 到期 → 自动进入金丝雀；
     - `deploy_now` → 跳过剩余等待立即部署；
     - `cancel` → 取消本次发布，**已排队补丁保留**，队首补丁自动开新周期；
     - 新补丁到达 → **仅 FIFO 入队**：不重置倒计时、不合并、数量不设上限；
  3. 并发底线：`max_active_deployments: 1`（同一时刻全局仅一个发布执行）；
  4. `query "status"` 返回 `{stage, approval, second_approval, deploy_command, queued_patches}`。
- **交付物**：延迟发布调度器、FIFO 队列、状态查询接口。
- **验收**：窗口四类事件集成测试全绿；worker 重启后队列与倒计时不丢；cancel 后队首补丁自动接续。
- **依赖**：WP10、WP11。

### WP13 金丝雀与自动回滚（W19–W22）

- **任务**：
  1. 制品晋级 → ArgoCD 下发 **5% 金丝雀**；
  2. 观察 5 分钟：错误率、P99 延迟（阈值取自 SLO）；
  3. 达标 → 全量发布；劣化 → **自动回滚** + 通知运维 + 事件升级；
  4. 全量后观察期，新异常事件自动关联本次变更标签。
- **验收**：健康指标达标自动晋级全量；人为注入劣化 → 自动回滚成功且通知到位。
- **依赖**：ArgoCD、制品仓库、SLO 阈值定义。

### WP14 全链路上线与演练（W22–W24）

- **任务**：
  1. 端到端 MTTR 指标采集与看板；
  2. 故障演练：回滚演练、熔断演练、全局 kill switch 演练、手动发布通道验证；
  3. 三期评审 → 正式全自动化上线。
- **验收**：MTTR 达标、回滚成功率 100%、全部演练通过。
- **依赖**：WP11–WP13 全部完成。

## 6. 验收指标总表

| 指标 | 所属期 | 建议目标值（评审时定稿） |
| --- | --- | --- |
| AI 根因 Top-1 命中率 | 一期 | ≥ 70% |

### 12.3 关键设计落地

1. **双模运行**：`mode.py` 缺省 production 且未配 `AIOPS_DATABASE_URL` 即 fail-fast；demo 经 `.env`/`demo-up.sh` 显式声明，演示数据（`data/`）原地保留，生产数据落 `data/prod/` 或 MySQL（详见设计说明书第 10 章）。
2. **令牌安全**：production 注册表仅存 sha256 指纹；轮换平滑（`previous` + 宽限期）；`demo` 明文键行为不变。
3. **kill switch 检查点**：刻意**不在** workflow 编排层检查（避免 Temporal replay 不确定性），改在 BFF 集中式中间件与 webhook 启动前检查。
4. **探针口径**：BFF `/api` 全量鉴权（httpGet 无法携带 Bearer）→ K8s 探针走无鉴权的 `/metrics`；此缺陷在 b9 验收中发现并修复。
5. **端口避让**：本机 compose prod profile 用 3316/6380（宿主机常驻 MySQL/Redis 会遮蔽 Docker 端口映射）；K8s 集群内不受影响。
6. **MySQL 严格模式适配**：`TEXT` 列禁止 `DEFAULT`（error 1101）——`monitored_apps.note` 由写入路径显式赋值；该缺陷在 b9 真实 MySQL 建表时暴露并修复。
7. **降级不中断**：MR 创建 recorded/degraded 双降级；限速无 Redis 退化为进程内；OTel 未配置完全 no-op。
