## 一、控制台易用性评估（配置 / 跟踪 / 可用性）

### 1.1 评估方法

实际启动控制台逐页走查（流程看板 / 流程列表 / 审批中心 / 发布窗口 / 审计回看 / 被监控应用 / 系统状态），并对 BFF 写接口、审计实现、审批交互做**代码与实测核验**。结论优先看「配置管理」，那是短板最集中处。

### 1.2 配置管理（短板最集中）

| # | 问题 | 证据 |
| --- | --- | --- |
| A1 | **配置面只打通不到 1/4**：UI 可维护的只有「被监控应用」；闸门策略、修复提供者/模型、沙箱镜像、通知 provider、稳定版端口、索引路径**全部**是 `.env`/YAML，需改文件 + 重启进程 | 写侧接口仅 `flows/*` + `monitored-apps`（`bff/app.py`）；系统状态页策略区只读 |
| A2 | **生效方式不一致且不告知**：被监控应用热生效；策略改了要重启，且**运行中流程用启动快照**，改了不生效。UI 无「需重启 / 对运行中流程不生效」提示 | `snapshot_for_workflow` 快照语义；`SystemPage` 无生效方式标注 |

### 1.4 可用性（安全与运行）

| # | 问题 | 证据 |
| --- | --- | --- |
| C1 | **BFF 完全无鉴权**：8 个写接口（含批准发布、删除监控项）全裸；默认绑 `127.0.0.1` 是唯一缓解，改 `--host 0.0.0.0` 即等于把「批准发布生产」开在网上 | `grep` 无 `Depends/middleware/auth`；无 CORS 中间件（对跨站 JSON 有一定默认缓解，不可当安全边界） |
| C2 | **配置类写操作有丢更新风险**：`PUT` 为「读-改-写」，并发编辑同一条会覆盖（已给高频 `toggle` 做专用接口规避，`PUT` 仍是读改写） | `bff/monitored_apps.py` `update()` |
| C3 | **轮询非推送**：审批 2s / 看板 5s / 系统状态 15s；倒计时用服务端时间校准（**做对了**），但动作生效有延迟、无确定性回执 | 各页 `refetchInterval`；`lib/api.ts` `serverNow()` |
| C4 | **无降级横幅**：Loki/Ollama/Docker 不可用不显性提示，而这些会让修复链路**静默降级为兜底补丁**；Temporal 断开仅左下角小点 | `Dashboard`/`SystemPage` 无降级提示区 |
| C5 | 窄视口体验一般：表格依赖横向滚动（容器确为 `overflow-x-auto`，可用）；窄屏按钮/KPI 换行 | 截图实测 |

### 1.5 建议（按优先级）

**P0 — 安全与正确性**

1. **给 BFF 加认证**，`actor` 从凭证取真实身份，替换写死的 `web-console`。（结构性改动，建议单独一轮）
2. **修审计目标链接**：配置类审计用独立字段（`target`）而非复用 `wf_id`；前端按 action 前缀决定是否可跳转。（**B1 为本轮实现引入，最小修复**）
3. **把「失败/异常」纳入流程终态分类**（看板 + 审计 + 流程列表），让挂掉的流程可见。

**P1 — 把「配置」做成一等公民**

4. 系统状态页逐项标注：当前值 / 来源（YAML·env·清单）/ **生效方式（热 or 需重启）** / 对运行中流程是否生效。
5. 审批确认框内联关键证据（diff 摘要 + 测试结论 + 置信度 + 影响文件数）+ 「查看完整详情」跳转。
6. 配置变更留痕加 **before/after diff**，支持一键回滚。

**P2 — 易用性打磨**

7. 被监控应用支持 **导入/导出 JSON、批量启停、复制条目**。
8. 表单**实时校验 + 字段级错误**。
9. 增加**降级提示横幅**（Loki/Ollama/Docker/Temporal 异常时提示「修复链路处于降级模式」）。

### 1.6 做得好的地方（不要改坏）

流程详情证据链完整（根因/补丁/测试报告/发布结果/审批记录/留痕文件 + 事件时间线）；服务端时间校准 + 倒计时；审批重复提交拦截（`_extra` 校验）；写操作一律留痕；被监控应用「读盘不缓存」的热生效实现干净；空状态文案齐备。
**问题不在「有没有」，而在「配置面太窄 + 审批点信息太少 + 无身份」。**

## 二、Qoder 沙箱可行性评估

**问题**：能否让 Qoder 同时承担「改代码 + 跑测试」，用 Qoder 自身的沙箱机制，从而不再额外部署容器？

### 2.1 核实到的事实

Qoder **确有**沙箱，且为内核级隔离（但归属 **IDE / Quest 桌面端**）：

| 平台 | 技术 | 强度 |
| --- | --- | --- |
| macOS | Seatbelt / `sandbox-exec`（`(deny default)` + 白名单） | 内核级 |
| Linux | bubblewrap（`--ro-bind`、`--tmpfs` 遮敏感路径、`--unshare-net`） | 内核级（容器内降级） |
| Windows | 自研 `sandbox.exe`（受限令牌 + 动态 DACL + Job Object） | 用户态，官方承认不能完全覆盖对抗性攻击 |

**沙箱语义**：工作区可写、其余目录只读、`~/.ssh` 等敏感路径不可见；网络**默认开**、可配全阻断、**无域名级过滤**。

**三条关键边界**

1. 归属 **Qoder IDE / Quest（桌面）**；实测 `qodercli --help`（v1.1.65）**无任何 sandbox 开关**——只有 `--permission-mode`（权限门禁）、`--tools/--allowed-tools/--disallowed-tools`（工具白名单）、`--worktree`（git 工作树），**均非隔离**。
2. 沙箱内命令失败会触发**权限升级**，且**必须在 IDE 里人工批准** → 无人值守会卡住。
3. 官方明示：**在 Docker 容器内使用 Qoder IDE 时沙箱隔离能力受限**，仅做文件系统与网络隔离。

**认知纠正**：现状**并未**「额外部署容器给 Qoder 用」——Qoder 跑在宿主上（`--permission-mode accept_edits` + 工具白名单 + 隔离工作区副本，评估时点**显式屏蔽 Bash**；2026-10-12 起自检模式改为受限放行测试命令 + hook 封闭，见 §2.3 治理进展）。Docker 容器是**测试与发布**在用。所以「去掉额外容器」省掉的恰是**唯一的独立裁决手段**。

### 2.2 风险

1. **职责分离被破坏（最关键）**：同一 agent 既改代码又判定「测试通过」＝自己给自己打分；可能跑错命令、漏测、把失败解释为环境问题，甚至改测试让其通过。
2. **自报不可信已有实证**：模型名小写 `deepseek-flash` → **静默回退 auto**，退出码 0、结果看似成功（见接入设计文档 §4.7）。连「用了哪个模型」都会不声不响地变，其「测试通过」不宜作门禁。
3. **隔离等级不对等**：

| 维度 | 我们的 Docker 沙箱 | Qoder 沙箱（IDE） | Qoder CLI（无头） |
| --- | --- | --- | --- |
| 内核隔离 | 容器命名空间 | ✅ | ❌ **无** |
| 环境可复现 | ✅ 固定镜像 | ❌ 宿主环境 | ❌ 宿主环境 |
| 出网 | ✅ `--network none` | ⚠️ 默认开 | ⚠️ 无控制 |
| 无人值守 | ✅ | ❌ 升级权限要人工点 | — |
| 判定依据 | 退出码（独立） | 自报 | 自报 |

### 2.3 选项与推荐

| 方案 | 内容 | 评价 |
| --- | --- | --- |
| **A（推荐）→ 已实施** | 保留独立沙箱做门禁，让 Qoder 做**自检**（prompt 要求跑目标测试 + 受限命令白名单 + PreToolUse hook 命令级封闭） | 改动最小、挡掉无效轮次省时间与 credits；门禁仍独立。**2026-10-12 已落地**（P2⑤/P2⑥），见下方「治理进展」 |
| B | 测试交给 Qoder，但结论标记 `self_reported`（不得标 `verified`） | 仅适合低风险/开发内环；须接受无内核隔离、可读写宿主、能上网、不可复现 |
| C（长期） | **按风险分级**：受保护目录/生产发布 → 必须独立沙箱；白名单小 diff → 可自检 + 抽检。落点 `release-gate-policy.yaml` 增 `testing.mode: sandbox \| self_report` | 折中，兼顾效率与安全 |
| D | 统一到 Qoder 沙箱：仅 **IDE/Quest 或云端会话**（`--remote` / `--remote-session` / `--remote-control`）可得真沙箱 | 代码需出本机，先过合规；**已实测否决（2026-10-12）**：`--remote` 硬性要求 GitHub 仓库（详见 §2.4），本地隔离工作区形态不可用 |

**结论**：Qoder 沙箱质量不错，但**是 IDE 能力不是 CLI 能力**，而无人值守链路跑 CLI →「用 Qoder 沙箱替代测试容器」当前形态**做不到**。可行的是让 Qoder 自检以提速，**门禁继续由我们的沙箱独立裁决**。

**治理进展（2026-10-12 更新）**：Option A 已实施并强化，形成三层防线——

1. **自检提速已落地（P2⑤）**：`AIOPS_QODER_SELF_CHECK`（默认开）放行 `unittest`/`pytest` 受限测试命令，让 Qoder 改动后先自检、提前拦无效候选省回炉轮次；**自检结论不参与任何闸门**（正确性仍由独立 Docker 沙箱裁决）；置 0 回退「Bash 全禁」旧行为。
2. **命令级封闭改由 PreToolUse hook 承担（P2⑥）**：实测证明 `--allowed-tools` 并非封闭白名单（见 §2.4 第三项），故新增 `aiops_agent/qoder_guard.py`，经 `--settings` 注入——白名单前缀 + 正向字符集防拼接注入 + fail-closed（解析失败/异常即拒），Bash/Monitor 双通道同规则；`AIOPS_QODER_HOOK_ALLOWED_PREFIXES` 可覆盖前缀。
3. **生产接线 E2E 已验证**：真实 CLI 经接入层生产参数运行——越权 `echo` 被 hook 拒绝、`unittest` 正常放行（10.8s / 0.053 credits）；接线回归用例已随 `tests/test_qoder_fix.py` 锁定。

**关键坑（已规避）**：`--settings` 注入的 hooks 属 CLI 内部 "flag" 源，与 `--setting-sources` **互斥**——显式传后者（合法值仅 user/project/local）必然过滤 flag 源、hook 静默失效；接入层已固定不传该参数。

### 2.4 未验证项补测结果（2026-10-12 完成，P2⑥）

三项均已用 qodercli v1.1.65 实测补齐：

| 未验证项 | 实测结论 |
| --- | --- |
| `--remote` 云端沙箱无人值守 | **不可用（exit=42）**：空目录报 `Cloud remote sessions currently require a GitHub repository`——硬性要求 GitHub 仓库（本地副本 + `git init` 的隔离工作区不满足），且代码须推送出境，与「本地隔离副本」设计前提和数据红线双重冲突。**结论：不采用** |
| macOS + CLI 隐式沙箱 | **不存在**：二进制字符串表无 `sandbox-exec`/`seatbelt` 实现；工作区外写入被 **permission 层**拒绝（权限门禁 ≠ 内核隔离）。CLI 无头模式隔离依赖宿主防线：权限模式 + 工作区副本 + 本次新增 hook 封闭 |
| 带参命令白名单匹配 | **`--allowed-tools 'Bash(...)'` 并非封闭白名单（证伪）**：白名单外 `echo` 照常执行；实现为 prefix/wildcard/exact 三种「免询问预授权」匹配；**Monitor 是第二条命令通道**（不受 Bash 参数约束，模型会偏好使用）；复合命令经 tree-sitter 拆解逐子命令匹配。**替代方案**：PreToolUse hook 是封闭的（exit 2 即拒、fail-closed），已据此实现 `qoder_guard.py` 并实测 4/4 场景通过（越权拒 / 测试放行 / Monitor 同规则 / 拼接注入拒） |
