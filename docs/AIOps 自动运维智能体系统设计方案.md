## 1. 背景与目标

### 1.1 背景

线上应用服务器异常（空指针、资源泄漏、配置错误等）依赖人工排查，平均修复周期长（MTTR 高），且夜间/节假日响应不及时。本系统通过「监控 → 分析 → 修复 → 测试 → 审批 → 延迟发布」的全链路自动化，将常规异常的处理从小时级压缩到分钟级，同时保留人工闸门确保变更可控。

### 1.2 目标

1. **自动发现与诊断**：秒级发现异常，自动完成日志取证与根因分析；
2. **自动修复与验证**：AI 生成最小化补丁，沙箱内自动完成测试验证；
3. **安全自动发布**：经运维审批 + 用户公告双重闸门后，延迟 15 分钟自动灰度发布，劣化自动回滚；
4. **全程可审计**：每一次 AI 变更、每一次审批、每一次发布均可追溯。

### 1.3 非目标

- 不替代架构级改造与需求迭代类开发；
- 不对鉴权、支付、加密等核心目录做全自动变更（需二级人工审批）；
- 不承诺 100% 无人值守：置信度不足、测试失败、金丝雀劣化等场景一律转人工。

## 2. 总体架构

系统自下而上分为五层，三道人工/策略闸门嵌入流程关键点：

```text
┌──────────────────────────────────────────────────────────────┐
│ 执行层  发布服务：审批闸门 → 用户弹窗+15分钟倒计时 → 金丝雀 → 全量 │
├──────────────────────────────────────────────────────────────┤
│ 验证层  测试沙箱：单元测试 / 回归测试 / SAST 静态扫描，质量门禁    │
├──────────────────────────────────────────────────────────────┤
│ 决策层  修复 Agent：Code RAG 检索 → 根因定位 → 生成最小补丁 diff  │
├──────────────────────────────────────────────────────────────┤
│ 分析层  异常检测：Drain3 日志聚类降噪 → LLM 根因判定 + 置信度评分  │
├──────────────────────────────────────────────────────────────┤
│ 感知层  监控采集：Prometheus 指标 / Filebeat 日志 / OTel 链路    │
└──────────────────────────────────────────────────────────────┘
```

| 闸门 | 位置 | 类型 | 机制 |
| --- | --- | --- | --- |
| 闸门 1 | 异常分析后 | 策略闸门 | LLM 根因置信度 < 0.8 → 转人工，不进入自动修复 |
| 闸门 2 | 测试通过后 | 人工闸门 | IM 交互卡片审批，超时自动驳回 + 电话升级；受保护目录需二级审批 |
| 闸门 3 | 审批通过后 | 用户闸门 | 全量用户弹窗公告 + 15 分钟倒计时，可取消、可加速、可被排队补丁不打断 |

## 3. 端到端流程

### 3.1 状态机

```text
DETECTED → TRIAGING → FIXING → TESTING → WAIT_APPROVAL → NOTIFYING → CANARY → ROLLING_OUT → DONE
              │          │         │            │             │           │
              ▼          ▼         ▼            ▼             ▼           ▼
        置信度<0.8    修复失败   测试失败     驳回/超时     运维取消     健康检查劣化
              │          │         │            │             │           │
              └─────────────────────┴────────────┴─────────────┴───────────┘
                                      ▼
                               ESCALATED（升级人工，全程审计留痕）
```

### 3.2 流程说明

| 阶段 | 动作 | 执行方 |
| --- | --- | --- |
| DETECTED | 指标越阈值 / 错误日志突增，生成告警事件 | 自动 |
| TRIAGING | 拉取日志与调用链，聚类降噪后由 LLM 输出结构化根因（错误类型、影响面、嫌疑文件、置信度） | 自动 |
| FIXING | RAG 检索代码库与历史工单，生成最小补丁 diff 与变更说明 | 自动 |
| TESTING | 隔离沙箱执行单测、回归、SAST，全过才放行 | 自动 |
| WAIT_APPROVAL | IM 卡片推送根因 + diff + 测试报告，运维放行/驳回/转人工 | 人工闸门 |
| NOTIFYING | 向全部在线用户弹出升级公告，进入 15 分钟发布倒计时 | 自动 + 用户感知 |
| CANARY | 到期自动部署 5% 金丝雀，观察错误率与 P99 延迟 | 自动 |
| ROLLING_OUT | 健康达标后全量发布；劣化自动回滚并通知 | 自动 |

## 4. 详细设计

### 4.1 感知层：监控采集

- **指标**：Prometheus 抓取应用与主机指标（QPS、错误率、延迟、资源水位），Alertmanager 按规则触发告警；
- **日志**：Filebeat / Fluent Bit 采集应用日志入 Loki（或 ELK），按服务与 trace_id 关联；
- **链路**：OpenTelemetry 汇总分布式调用链，为根因分析提供跨服务上下文；
- **触发条件**：指标越阈值或单位时间错误日志数突增（同比/环比基线），生成标准告警事件 `Alert{alert_id, service, severity, description}`，作为整个流程的唯一入口。

### 4.2 分析层：异常检测

1. **降噪去重**：Drain3 对日志做模板聚类，同模板海量重复日志聚合为计数，避免淹没 LLM 上下文；
2. **根因判定**：LLM 结合聚类结果、调用链、近期变更记录（git diff）、历史工单库，输出结构化根因：

- `error_type`：错误类型；
- `suspect_files`：嫌疑文件列表；
- `confidence`：置信度（0~1）；
- `summary`：自然语言根因说明。

3. **输出约束**：置信度 < 0.8 直接转人工（闸门 1），流程结束并留痕。

### 4.3 决策层：AI 代码修复

- **代码检索（RAG）**：代码仓库按 AST 语义切块建向量索引，检索相似缺陷的历史修复方案作为参考上下文；
- **补丁生成**：修复 Agent 生成**最小化 diff**，附变更说明与风险评估；优先单点修复，禁止顺手重构；
- **变更白名单**：仅允许修改白名单目录；命中 `auth/**`、`payment/**`、`crypto/**` 的补丁自动升级要求**二级人工审批**（闸门 2 扩展）；
- **可追溯**：补丁元数据打标签 `ai-fix: {alert_id, model_version, confidence}`。

### 4.4 验证层：测试沙箱

- 补丁在**隔离沙箱**（独立 K8s Job + gVisor/Firecracker 强隔离运行时）中执行：

1. 依赖安装与环境构建；
2. 单元测试 + 回归测试；
3. SAST 静态扫描（禁止引入高危漏洞/敏感信息硬编码）。

- **质量门禁**：任一环节失败则回炉重试（限次，防 token/资源雪崩）；仍失败转人工（ESCALATED）。

### 4.5 闸门 2：运维确认

- **通知方式**：飞书 / 钉钉 / Slack 交互卡片，含根因分析、完整 diff、测试报告、回滚预案四个部分；
- **操作**：一键「放行 / 驳回 / 转人工修改」；受保护目录补丁追加二级审批卡片；
- **超时策略（已锁定）**：等待 30 分钟无响应 → **自动驳回**，同时电话/短信升级通知值班负责人；驳回即关闭本次修复流程并留痕；
- **人工在环原则**：系统默认站在安全侧——所有不确定路径（超时、弃权、接口异常）均走向驳回或转人工，绝不自动放行。

### 4.6 闸门 3：用户通知 + 15 分钟延迟发布（核心设计）

#### 4.6.1 触发与公告

运维审批通过后：

1. 通过 **WebSocket 向所有在线会话推送站内弹窗** + 页面 Banner，可选 App Push：

> 【系统通知】新版本 vX.Y.Z 已完成验证，将于 15 分钟后部署。期间可能出现短暂抖动，如有异常请点击反馈。

2. 公告内容与发布时间入审计日志。

#### 4.6.2 持久化延迟队列

- 部署任务写入**持久化延迟队列**（Temporal 定时器 / Redis ZSET / MQ 延迟消息），服务重启、发布 worker 宕机均不丢失任务；
- 倒计时以服务端时间为准，客户端只做展示。

#### 4.6.3 窗口事件处理（已锁定策略）

15 分钟倒计时窗口内可能出现四类事件，处理规则：

| 事件 | 处理规则 |
| --- | --- |
| 倒计时到期 | 自动进入金丝雀发布（默认出口） |
| 运维下发 `deploy_now` | 跳过剩余等待，立即部署 |
| 运维下发 `cancel` | 取消本次发布；**已排队补丁保留**，队首补丁自动开启新周期 |
| 新补丁到达 | **仅进入 FIFO 队列**：不重置倒计时、不与当前补丁合并、排队数量不设上限 |

#### 4.6.4 用户反馈（已锁定策略）

- **不设熔断阈值**：用户反馈不触发自动取消；
- 反馈入口仅作为信息收集通道，是否取消由运维人工决策；
- 出口收敛为三种：到期自动部署 / 运维加速 / 运维取消。

#### 4.6.5 状态迁移

```text
NOTIFYING（倒计时中）
  ├── 到期 ───────────────→ CANARY（自动部署）
  ├── 运维 deploy_now ──────→ CANARY（立即部署）
  ├── 运维 cancel ──────────→ CANCELLED（队列保留，队首开新周期）
  └── 新补丁到达 ───────────→ 仅入队（NOTIFYING 不变，不重置计时）
```

### 4.7 灰度发布与自动回滚

1. 制品晋级 → 通过 ArgoCD 下发 **5% 金丝雀**；
2. 观察 5 分钟，健康指标：错误率、P99 延迟（阈值取自 SLO）；
3. 达标 → 全量发布；劣化 → **自动回滚** + 通知运维 + 事件升级；
4. 全量后进入观察期，新产生的异常事件自动关联本次变更标签。

## 5. 关键策略决策表（已锁定）

| # | 决策点 | 锁定结论 |
| --- | --- | --- |
| 1 | 审批超时策略 | 30 分钟未响应 → 自动驳回 + 电话升级，默认安全侧 |
| 2 | 窗口内新补丁 | 仅 FIFO 排队：不重置倒计时、不合并、排队数量不设上限；当前发布结束/取消后队首补丁自动开新周期 |
| 3 | 用户反馈熔断 | 不设阈值，反馈不自动取消发布，仅保留人工取消 |
| 4 | 受保护目录 | `auth/**`、`payment/**`、`crypto/**` 需二级人工审批 |
| 5 | 并发底线 | 同一时刻全局仅允许一个发布在执行（保留项，非阈值） |

对应配置见 `release-gate-policy.yaml`，工作流启动时加载快照，运行期不热修改。

### 5.1 单机生产化整改关键决策（ADR 摘要，2026-10-13）

对应《单机生产化整改实施计划》批次 A–I；实施状态与证据标记见《实施计划》第 13 节。按计划要求不额外建立 ADR 文件，决策与代价在此记录：

| 决策 | 选定方案及代价 | 不采用的方案 |
| --- | --- | --- |
| 事件协调 | 复用 SQLAlchemy/MySQL 事务与唯一约束；demo 保留轻量后端 | 不新增消息队列，不用 Redis 易失键承担告警事实存储 |
| HTTPS | 本机 Caddy 反代，OpenSSL 签发静态本地 CA 证书；增加一个受托管代理进程 | 不自写 TLS 代理，不让容器代理依赖宿主 loopback 可达假设 |
| Temporal | 同主机正式 Server，独立业务库/visibility 库及 namespace | 不在线转换 SQLite，不把 start-dev 更换数据文件后称为生产 Server |
| MCP | production 只支持 stdio，每个调用者使用自己的最小权限 BFF 凭证 | 本轮不开发多用户 HTTP OAuth 网关 |
| 发布互斥 | 本机文件锁加持久化发布记录，锁定真实目标资源 | 不将进程内锁、活动重试或临时租约视为发布幂等 |
| 备份 | 本机加密归档、定时任务、隔离恢复验证，预留异地同步配置 | 不将本机副本称为异地容灾 |

适用边界：单主机执行发布。未来引入第二台执行主机时，必须重新设计共享目标锁与执行隔离，不能直接扩容 worker。

## 6. 安全护栏

| 类别 | 措施 |
| --- | --- |
| 变更范围 | 白名单目录 + 核心目录二级审批；AI 禁止顺手重构 |
| 频率限制 | 同一服务 24h 内 AI 自动修复次数上限，防修复风暴 |
| 幂等防重 | workflow id 幂等启动（`WORKFLOW_ID_REJECT_DUPLICATE`），重复告警不重复开流程 |
| 审计 | Temporal 事件历史天然留痕；补丁标签含模型版本与置信度 |
| 降级开关 | 保留手动发布通道与全局 kill switch，一键切回纯人工模式 |
| 沙箱隔离 | 测试在 gVisor/Firecracker 隔离环境执行，补丁无出网权限 |

## 7. 技术选型

| 模块 | 选型 | 说明 |
| --- | --- | --- |
| 监控/日志/链路 | Prometheus + Grafana + Loki + OpenTelemetry | 指标、日志、调用链三管齐下 |
| 异常检测 | Drain3 + LLM triage | 聚类降噪 + 语义根因判定 |
| 工作流编排 | **Temporal** | 原生支持定时器、人工 signal、持久化，最适合闸门场景 |
| 代码 RAG | AST 切块 + 向量库（FAISS / 纯 Python 双后端） | 检索相似历史修复；按 service 专属索引自动构建、仓库变更自动重建 |
| 代码修复引擎 | 本地 LLM（Ollama，默认，`qwen3.8:27b-mlx`）/ Qoder CLI 无头（可选） | 双提供者运行时可切换；失败安全侧降级不中断流程 |
| CI/CD | GitLab / GitHub / Gitee MR 真实创建 + ArgoCD | 沙箱测试 + GitOps 发布（三平台已实现，见 `git_integration.py`） |
| 测试沙箱 | Docker 容器隔离（已落地）/ K8s Job + gVisor（集群路径） | 强隔离执行测试（`--network none` 等） |
| 通知 | 飞书/钉钉交互卡片 + 回调解析；站内弹窗（生产接线项） | 运维卡片已落地；WebSocket 弹窗推送待生产网关接入 |
| 配置管理 | YAML + pydantic 强校验 | 策略即配置，可评审可回滚 |

## 9. 非功能性设计

| 维度 | 设计 |
| --- | --- |
| 可靠性 | 延迟队列持久化；worker 宕机任务不丢；活动重试有限次并指数退避 |
| 可观测性 | 每阶段状态可查（query）；指标：各闸门通过率、MTTR、回滚率、AI 修复采纳率 |
| 确定性 | 工作流内禁止非确定性调用；策略以启动快照为准，运行期变更走版本升级 |
| 性能 | 日志聚类在采集侧完成；LLM 调用带超时与重试上限；沙箱并发受配额限制 |
| 扩展性 | 新增闸门 = 新增状态 + signal；新服务接入 = 配置告警规则，零代码 |

## 10. 落地路线图

| 阶段 | 范围 | 验收标准 |
| --- | --- | --- |
| 一期（1-2 月） | 监控 + 日志异常分析 + AI 修复**建议**（人工执行发布） | AI 根因 Top-1 命中率、修复建议采纳率达到阈值 |
| 二期 | 沙箱自动测试 + 自动创建 MR + 运维审批闸门 | 测试通过率、审批平均时长可统计 |
| 三期 | 用户弹窗 + 15 分钟延迟发布 + 金丝雀自动回滚（全自动化） | 端到端 MTTR 指标、回滚成功率达标 |

全程保留一键降级开关；每期上线前做故障演练（含回滚与熔断演练）。

> 现状（2026-10-12）：三期能力均已落地并经端到端验证——AI 根因/修复建议、沙箱自动测试、MR 真实创建、运维审批闸门、用户公告 + 延迟发布 + 金丝雀自动回滚；控制台（BFF + SPA）、可用性巡检、日志采集与需求基线闭环均已上线。

## 11. 风险与应对

| 风险 | 应对 |
| --- | --- |
| AI 误修引入新缺陷 | 三道闸门 + 沙箱测试 + 金丝雀 + 自动回滚；置信度闸门拦截低质量修复 |
| LLM 幻觉生成不存在 API 的代码 | RAG 以真实代码库为上下文；补丁必须通过编译与测试才到审批 |
| 审批疲劳导致超时频发 | 超时自动驳回 + 电话升级；定期评审阈值与值班排班 |
| 15 分钟窗口内补丁排队过多 | 队列不设上限但同一时刻仅一个发布执行；超量时人工介入排序 |
| 用户公告后体验受损引发投诉 | 公告内容明确影响范围与时间；反馈通道直达运维 |
